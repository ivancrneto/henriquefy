# eventex

**What it is.** The Welcome to the Django project: a conference site with a landing page,
speakers, talks, courses and a subscription form that emails a confirmation. Two Django apps
(`core`, `subscriptions`), 128 `def`s outside migrations, 13 test modules, Django 3.1.2 with
python-decouple, Heroku deployment. The repository was created in 2015; at the manifest commit
the Python files were regenerated on Django 3.1.2 (`eventex/settings.py:4`, "Generated by
'django-admin startproject' using Django 3.1.2."), so the code documents 2020 practice. Two
facts about the clone matter for citation. It is shallow (50 commits reachable) and 49 of
those commits, all from 2020-11-03 to 2020-11-05, carry the author `Giandoso`; the only commit
by Henrique is HEAD, from 2023-11-29, which adds `contrib/landingpage.zip`. The files are what
his repository publishes, so this digest cites them, but no commit message is quoted as his
words. The repo has no license: excerpts below are quotation-length.

**How he tests.** Runner: Django's own, `python manage.py test` (`README.md:23`,
`.travis.yml:9`), with `django.test.TestCase` everywhere; no pytest, no fixtures beyond one
JSON file. Layout: a `tests/` package inside each app, one module per unit named by kind and
subject: `test_model_speaker.py`, `test_view_home.py`, `test_form_subscription.py`,
`test_mail_subscribe.py`, `test_admin.py`. Inside a module, one class per scenario, named
`<Subject><Scenario>`: `SubscriptionsNewGet`, `SubscriptionsNewPostValid`,
`SubscriptionsNewPostInvalid` (`eventex/subscriptions/tests/test_view_new.py:8, 42, 59`);
`SpeakerDetailGet`, `SpeakerDetailNotFound` (`eventex/core/tests/test_view_speaker_detail.py:5, 41`).
`setUp` performs the action (the GET, the POST, the create) and every test method makes one
assertion about one consequence (`test_view_new.py:9-39`). Docstrings are the spec, in English
and imperative: `"""GET / must return status code 200"""` (`eventex/core/tests/test_view_home.py:12`),
`"""Email and Phone are optional, but one must be informed."""`
(`eventex/subscriptions/tests/test_form_subscription.py:38`). Lists of expected content are
checked in a `for` with `self.subTest()` (`test_view_home.py:25-36`; `test_view_talk_list.py:32-47`
with counts). URLs are always resolved by name through `from django.shortcuts import resolve_url as r`
(`test_view_home.py:2, 9`), never typed as paths. Model tests check field metadata
(`Speaker._meta.get_field('description').blank`, `test_model_speaker.py:19-25`) and
`__str__`, `get_absolute_url`, ordering (`test_model_talk.py:41-45`). Manager tests use
`assertQuerysetEqual` with a lambda (`test_model_contact.py:62-70`). Mail is asserted through
`django.core.mail.outbox` (`test_mail_subscribe.py:11-37`). The one mock is a hand-made
monkeypatch of `message_user` on the admin class, restored by hand
(`eventex/subscriptions/tests/test_admin.py:26-37`). Form tests build on a factory
`make_validated_form(**kwargs)` over a valid dict and a custom assertion
`assertFormErrorCode` (`test_form_subscription.py:42-59`). Not tested: the three override
branches of `EmailCreateMixin` (`eventex/subscriptions/mixins.py:25-26, 32-33, 37-38`), the
`SpeakerModelAdmin` display helpers (`eventex/core/admin.py:17-35`), and the validators on
their own (only through the form).

**How he handles errors.** No exception class is declared and there is no `try`/`except` in
app code. Validation failures are Django `ValidationError`s raised with a code:
`raise ValidationError('CPF deve conter apenas números.', 'digits')` and
`raise ValidationError('CPF deve ter 11 números.', 'length')`
(`eventex/subscriptions/validators.py:6, 9`); the cross-field rule raises in `clean`:
`raise ValidationError('Informe seu e-mail ou telefone.')` (`eventex/subscriptions/forms.py:27-28`).
The tests assert on the code, not the message (`test_form_subscription.py:15, 20, 42-46`), so
the message can change freely. What reaches the boundary is Django's: `DetailView` returns
404 for a missing slug or pk, asserted in `test_view_speaker_detail.py:41-44` and
`test_view_detail.py:36-39`; custom `400.html`, `403.html`, `404.html`, `500.html` templates
exist. `config('SECRET_KEY')` has no default (`eventex/settings.py:26`), so a missing `.env`
fails at import, loudly, before anything runs.

**Naming and interface.** Identifiers in English, user-facing strings in Portuguese: every
model field carries a Portuguese `verbose_name` (`eventex/core/models.py:8-12`), the URL paths
are Portuguese (`inscricao/`, `palestrantes/<slug:slug>`, `palestras/`, `eventex/urls.py:24-26`)
while the URL names and views are English (`home`, `speaker_detail`, `talk_list`, `new`,
`detail`). Views are module-level callables built with `as_view`, not subclasses:

```python
home = ListView.as_view(template_name='index.html',
                        model=Speaker)

speaker_detail = DetailView.as_view(model=Speaker)

talk_list = ListView.as_view(model=Talk)
```
(`eventex/core/views.py:6-11`; same shape in `eventex/subscriptions/views.py:7-11`). Query
vocabulary lives in querysets with domain names:

```python
class PeriodQuerySet(models.QuerySet):
    MIDDAY = '12:00'

    def at_morning(self):
        return self.filter(start__lt=self.MIDDAY)

    def at_afternoon(self):
        return self.filter(start__gte=self.MIDDAY)


PeriodManager = models.Manager.from_queryset(PeriodQuerySet)
```
(`eventex/core/managers.py:12-22`), so templates read `talk_list.at_morning`
(`eventex/core/templates/core/talk_list.html:7, 14`) and admin reads
`obj.contact_set.emails().first()` (`eventex/core/admin.py:28`). Choices are class constants
(`Contact.EMAIL`, `Contact.PHONE`, `models.py:26-32`) and tests use them, never the letter.
The mixin follows Django's own hook convention, `email_to` attribute plus `get_email_to()`
(`mixins.py:8-9, 31-34`). The subscriptions URLconf is namespaced (`app_name = 'subscriptions'`,
`eventex/subscriptions/urls.py:4`) and reversed as `subscriptions:new`. The public surface of
each app is its URLs and admin; nothing is marked private.

**Packaging, config, tooling (2020).** Not a package: no `setup.py`, no `pyproject.toml`.
Dependencies are twelve exact pins in `requirements.txt:1-12` (Django 3.1.2, python-decouple
3.3, dj-database-url, dj-static, gunicorn, psycopg2-binary, django-extensions, and his own
`django-test-without-migrations==0.6`); `requirements-dev.txt:1-2` adds an unpinned `jupyter`.
Python is fixed by Heroku's `runtime.txt:1` (`python-3.6.1`) and `.travis.yml:3`. Settings
follow python-decouple end to end:

```python
SECRET_KEY = config('SECRET_KEY')

DEBUG = config('DEBUG', default=False, cast=bool)

ALLOWED_HOSTS = config('ALLOWED_HOSTS', default='', cast=Csv())
```
(`eventex/settings.py:26-31`); the database is `config('DATABASE_URL', default=default_dburl, cast=dburl)`
with a sqlite default (`:84-87`); the six `EMAIL_*` settings are read with casts and no
defaults (`:129-135`). `contrib/env-sample:1-9` lists every key with safe development values
(`SECRET_KEY=THIS_IS_NOT_A_GOOD_SECRET`, console email backend); `.gitignore:2` ignores `.env`;
`contrib/secret_gen.py:8-9` generates a production key; `README.md:36-46` sets each value with
`heroku config:set`. CI is Travis: install from requirements, `cp contrib/env-sample .env`,
`makemigrations`, `manage.py test` (`.travis.yml:4-9`). No linter, no formatter, no type
checker, no Makefile; indentation is tabs in some files and spaces in others (see Caveats).
Static files are served by `dj_static.Cling` in `eventex/wsgi.py:11, 16`.

**Caveats.**
- Status codes are bare integers in every view test: `self.assertEqual(200, self.response.status_code)`
  (`eventex/core/tests/test_view_home.py:13`; also `test_view_speaker_detail.py:18, 44`,
  `test_view_talk_list.py:26`, `test_view_detail.py:17, 39`, `test_view_new.py:14, 65`). The
  API course adopts `http.HTTPStatus` to end magic numbers (`kb/courses/design-api-na-pratica.md:162`).
- `EmailCreateMixin.get_email_template_name` recurses forever when `email_template_name` is
  set: it returns `self.get_email_template_name()` instead of the attribute
  (`eventex/subscriptions/mixins.py:25-26`). The branch has no test, which is why it survived.
- `CourseModelTest.test_ordering` asserts `Talk._meta.ordering`, not `Course`
  (`eventex/core/tests/test_model_talk.py:94-95`); the same file imports `Course` twice
  (`:4`).
- `SubscriptionDetailGet.test_html` puts the loop inside one `subTest` instead of one
  `subTest` per item (`eventex/subscriptions/tests/test_view_detail.py:31-33`), so the first
  failure hides the rest; every other test does it the right way round.
- `SubscriptionFormOld` is dead code left from the forms.Form stage of the course
  (`eventex/subscriptions/forms.py:7-11`).
- `test_email` and `test_phone` create a `contact` they never use and assert only
  `Contact.objects.exists()` (`eventex/core/tests/test_model_contact.py:14-30`).
- Tabs in `eventex/subscriptions/admin.py:7-31`, `apps.py:5-6` and most of the test files
  (`test_view_home.py`, `test_admin.py`, `test_form_subscription.py`, `test_mail_subscribe.py`,
  `test_model_subscription.py`, `test_view_detail.py`, `test_view_new.py`), spaces elsewhere.
  Nothing in the repo would catch it; the 2026 repos run `ruff format --check`.
- `email_from = settings.DEFAULT_FROM_EMAIL` is read at class-definition time
  (`mixins.py:11`), so an `override_settings` in a test would not reach it.
- `settings.py` mixes `Path` (`:19`) with `os.path.join(BASE_DIR, ...)` (`:84, 127`).
- `test_without_migrations` and `django_extensions` sit in the production `INSTALLED_APPS`
  (`settings.py:44-45`); there is a single settings module, so development tooling ships.
- `Course(Talk)` is multi-table inheritance where the OO course prefers composition
  (`kb/courses/oo-na-pratica.md:1341`); the cost shows in `TalkModelAdmin.get_queryset`
  filtering `course=None` to keep courses out of the talk list (`eventex/core/admin.py:38-41`).
- Typos in user-facing text: "forma marcadas" (`eventex/subscriptions/admin.py:27`), "vocie"
  (`subscription_email.txt:14`); in tests, `test_tempate` (`test_view_talk_list.py:28`).
- Authorship: 49 of the 50 reachable commits are not his (see "What it is"). The commit
  messages (`Refactor install ListView`, `Course migration abc to mti`, ...) narrate the
  course's refactoring sequence but cannot be cited as his words.
